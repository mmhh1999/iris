Status: initial survey, session 1. Scope per project brief — IRIS's lineage, indoor inverse rendering broadly, outdoor/daylight-aware neural rendering, sun/shadow geometry estimation, window & environment-map estimation, and transparent/transmissive material recovery. Compiled via web search in September 2026; coverage is necessarily a sample of an active field, not exhaustive. Every entry below was checked against at least an abstract/README (via WebSearch/WebFetch); entries marked "(abstract only, fields not fully confirmed)" mean I could not extract every table column with confidence from the source(s) reachable and the cell says "not stated in abstract" rather than guessing.

## 1. IRIS lineage

The two papers this project directly extends. Read in depth (IRIS via direct code audit of this repo; FIPT via its paper/README/GitHub, since IRIS's codebase is explicitly forked from it).

| | **IRIS** | **FIPT** |
|---|---|---|
| Citation | Lin, Huang, Li, Dong, Richardt, Li, Zollhöfer, Kopf, Wang, Kim. "IRIS: Inverse Rendering of Indoor Scenes from Low Dynamic Range Images." CVPR 2025. arXiv:2401.12977. Meta/UIUC/UMD. | Wu, Zhu, Yaldiz, Zhu, Cai, Matai, Porikli, Li, Chandraker, Ramamoorthi. "Factorized Inverse Path Tracing for Efficient and Accurate Material-Lighting Estimation." ICCV 2023 (also circulated as "FIPT"). UCSD et al. |
| Problem | Recover PBR material, spatially-varying HDR lighting, and an unknown camera response function (CRF) from **LDR** multi-view images of a room — removing the HDR-capture requirement that prior indoor inverse-rendering work assumed. | Jointly estimate material and lighting for indoor scenes from **HDR** multi-view images and known geometry, resolving reflectance/emission ambiguity faster than full inverse path tracing. |
| Representation | Fixed external mesh (from BakedSDF/SDFStudio or ScanNet++ scan) as the only geometry; per-point BRDF via an instant-NGP-style hash-grid MLP (`NGPBRDF`); voxel Surface Light Field (SLF) as a cached radiance/irradiance proxy on scene surfaces. | Same class of fixed reconstructed mesh; BRDF and emission mask networks; a volumetric surface light field as a radiance cache to avoid full recursive path tracing during optimization. |
| Lighting model | **Exactly two local terms, both zero unless a ray hits reconstructed geometry**: (1) per-triangle constant-radiance area emitters, flagged by saturated-pixel heuristics; (2) the voxel SLF as a cached diffuse-radiance/irradiance field. No environment/sky/background term exists (`model/emitter.py` comments "assume zero background lighting" for any ray that misses the mesh). | Same two-term structure (emitter mask + SLF radiance cache) — IRIS inherits this architecture essentially unchanged and adds CRF/LDR handling on top. |
| Material model | `NGPBRDF`: albedo (3ch sigmoid) + roughness (1ch, bounded) + metallic (1ch sigmoid) → GGX metallic-roughness BRDF via Lambertian diffuse + Smith-GGX specular + Schlick Fresnel. No opacity, IOR, or transmission channel anywhere; the Mitsuba-side `FIPTBSDF` wrapper declares only `DiffuseReflection`. | Same metallic-roughness BRDF family; FIPT is the origin of this material parameterization, IRIS reuses it near-verbatim. |
| Required data | Multi-view **LDR** posed images, externally reconstructed mesh, (synthetic) GT albedo/roughness/emission for supervision comparisons, (real) segmentation + an "intrinsic albedo" prior image (IRISFormer/RGB-X) as a soft prior. No EXIF/timestamp/GPS/solar metadata loaded by any dataset adapter (`utils/dataset/*`). | Multi-view **HDR** posed images + mesh + semantic segmentation masks. |
| Supervision | Self-supervised photometric reconstruction against LDR pixels, staged across 9 training scripts (SLF bake → emitter extraction → joint init → shading bake → BRDF/CRF training → SLF refine → emitter refine → final shading refine), plus the RGB-X/IRISFormer intrinsic-image prior as an auxiliary loss term on real data. | Self-supervised photometric reconstruction against HDR pixels via factorized path tracing; no CRF stage needed since input is already HDR. |
| Sun direction explicit | **No.** No solar/temporal metadata is loaded anywhere; nothing resembling a directional light exists in the model. | No — same limitation, inherited. |
| Sky illumination explicit | **No.** Confirmed by repo-wide grep for `sun|sky|environment ?map|envmap|outdoor|window|daylight|hdri|ibl` across the codebase: zero relevant hits. | No — FIPT was designed and evaluated on interior-lit indoor scenes (lamps, ceiling lights), not daylight. |
| Windows/transmission | **No first-class window entity anywhere**; whatever geometry a glazed opening occupies (if the SDF/NeRF mesh reconstruction closed it at all) is forced through the same opaque reflective BRDF, or, if it's bright enough, misclassified as an area emitter — the floor/wall is modeled as literally glowing rather than as a surface lit by transmitted daylight. | Same underlying limitation — FIPT was never evaluated on daylight/window scenes. |
| Relighting evaluated under novel illumination? | Only via `render_relight.py`'s manual Mitsuba-scene-dict editing (add/move/recolor emitters by hand) — a controlled edit of the *fitted local emitters*, not evaluation against an independently captured ground-truth relit condition. No held-out lighting-condition benchmark. | Same — relighting demonstrated by editing recovered local emitters, not validated against a second real capture under different illumination. |
| Main limitations (as relevant here) | Confirmed by direct code audit: zero background/environment radiance (hard zero, not merely "usually small"); purely opaque BRDF; no window/aperture concept; no solar/temporal metadata support; emitter-classification heuristic (saturated-pixel threshold) will misclassify a sun patch as a glowing floor rather than as evidence of an external directional source. | Purely local-emitter model designed for artificial/interior lighting; no daylight, no directional-sun term, no sky term, no transmissive material — all issues IRIS inherited unchanged. |
| What could transfer to IRIS | N/A (this *is* the baseline). | FIPT's factorized/cached radiance-field machinery (the SLF) is architecturally the right place to *attach* a sky-visibility or window-transmittance cache term, since it already exists as a per-voxel cached radiance query point in the renderer — a "does this voxel see sky through a window" visibility field could piggyback on the same data structure rather than requiring a new one. |

**Nuance on FIPT→IRIS lineage.** The architecture audit in this repo (`IRIS_ARCHITECTURE_AUDIT.md`) confirms IRIS's `model/emitter.py`, `model/brdf.py`, and the general 9-stage bake/train pipeline are a near-direct continuation of FIPT's structure, with IRIS's actual novel contributions concentrated on (a) the CRF-aware LDR→HDR handling and (b) the joint BRDF+CRF+emitter optimization schedule. Neither paper's core illumination/material representation changed in a way that touches the outdoor-daylight problem — meaning any daylight-aware extension is modifying an architecture whose two-term "local emitter + local radiance cache" design is shared by *both* papers, not an IRIS-specific quirk. This raises the ceiling of what such an extension could be relevant to (it would generalize back to FIPT and its descendants too) but also means there is no existing partial daylight support in either codebase to build from.

## 2. Indoor inverse rendering (broader 2022–2026)

Single/multi-view scene-level material+lighting decomposition, not window/daylight-specific but establishes the state of the art IRIS sits inside.

| Method | Venue/Year (arXiv) | Representation | Lighting model | Material model | Data required | Sun/sky/windows |
|---|---|---|---|---|---|---|
| **OpenRooms** | 3DV 2021 (arXiv:2007.12868) | Dataset/framework: 3D-scanned rooms + physically-based renders | Spatially-varying HDR envmaps per pixel/location, artificial + some window-lit scenes | Microfacet SVBRDF ground truth | Synthetic HDR renders + 3D scan geometry | Partial — dataset includes some window openings but not modeled as a distinct paper contribution; it's a data resource, not a daylight method |
| **InteriorVerse** | dataset paper (used by IRISFormer/RGB-X-era work) | Artist-designed synthetic rooms, GGX BRDF renders | HDR envmap-based, richer than OpenRooms | GGX SVBRDF ground truth | Synthetic HDR + geometry/material annotations | Not specifically daylight/window-focused |
| **MAIR** | CVPR 2023 (arXiv:2303.12368) | Multi-view scene decomposition (extends OpenRooms to multi-view) | 3D spatially-varying lighting volume (per-voxel incident illumination), enabling object insertion anywhere in 3D | SVBRDF | Multi-view HDR (synthetic, extended OpenRooms) + real-world test | Not addressed; artificial/interior lighting assumed |
| **MAIR++** | 2024 (arXiv:2408.06707) | Same lineage as MAIR | Implicit lighting representation (replaces explicit lighting volume for efficiency/quality) | SVBRDF | Multi-view HDR | Not addressed |
| **SIR** | 2024 (arXiv:2402.06136) | SDF-based neural radiance field | Learns shadows explicitly as a decomposable term (addresses reflectance/shadow ambiguity under intense local lighting) | 3-stage SVBRDF estimation with BRDF regularization | Posed multi-view **HDR** images | Not addressed; targets "intense indoor lighting" (lamps/spotlights), not daylight/windows |
| **Learning-based Inverse Rendering w/ Differentiable Monte Carlo Raytracing** | SIGGRAPH Asia 2022 (arXiv:2211.03017) | Learned material/lighting fields + differentiable MC path tracing refinement | Envmap / area-light hybrid, refined via differentiable rendering | SVBRDF | Multi-view (synthetic OpenRooms-style + real) | Not addressed |
| **IRISformer** | CVPR 2022 (arXiv:2206.08423) | Dense ViT for single-image inverse rendering | Per-pixel SH lighting predicted from a single image | Per-pixel SVBRDF | Single LDR/HDR image | Not addressed; this is the "intrinsic albedo prior" network IRIS itself uses on real scenes |
| **GLOW** | 2025 (arXiv:2511.22857) | Global-illumination-aware inverse rendering with co-located light+camera capture rig | Calibrated point light (from SfM-calibrated co-located flash), not natural illumination | SVBRDF with explicit global-illumination modeling | Multi-view images from a co-located light/camera capture device | Not daylight; deliberately avoids natural illumination ambiguity by using a calibrated point source instead |
| **AEGIR** | 2025/2026 (arXiv:2606.28635) | Gaussian-splatting-based indoor inverse rendering | Explicit area-emitter modeling within a 3DGS scene | Gaussian-attached material parameters | Multi-view images | Not addressed; area emitters modeled are interior fixtures, same class of assumption as FIPT/IRIS |
| **DNF-Intrinsic** | 2025 (arXiv:2507.03924) | Diffusion-based intrinsic decomposition, deterministic/noise-free | Learned via diffusion prior rather than explicit physical model | Intrinsic albedo/material maps | Single or few images | Not addressed |

**Takeaway for this section:** the entire "indoor inverse rendering" literature line (OpenRooms → MAIR/MAIR++ → SIR → FIPT/IRIS → GLOW/AEGIR) treats illumination as either (a) an unconstrained spatially-varying envmap/volume fit purely from pixel evidence, or (b) local emitters (lamps, calibrated flash). None of the papers surveyed model an explicit sun direction, sky dome, or window aperture as first-class scene entities — daylight, where present in a dataset (e.g. OpenRooms scenes with windows), is absorbed into the same generic "spatially varying lighting volume/envmap" representation as any other light, with no physical decomposition into direct-sun + sky + transmittance.

## 3. Outdoor / daylight-aware neural rendering (NeRF-OSR lineage and successors)

This is the section closest in *spirit* to the target problem (explicit sun+sky decomposition), but entirely for **outdoor** scenes — no window/indoor-transmission component anywhere.

| Method | Venue/Year (arXiv) | Representation | Lighting model | Sun explicit? | Sky explicit? | Material model | Required data | Relighting under genuinely novel illumination? |
|---|---|---|---|---|---|---|---|---|
| **NeRF-OSR** | ECCV 2022 (arXiv:2112.05140) | NeRF | Spherical-harmonics (SH) global illumination model; separate shadow network | Partial — SH captures directionality but no explicit discrete "sun vector"; azimuth is loosely calibrated per-session from capture metadata | Yes, via the same SH basis (not separated from sun) | Diffuse albedo (implicit in radiance decomposition; not a full PBR BRDF) | Multi-session outdoor photo collections (their benchmark: 8 building sites, 3240 views across 110 sessions/times) + an environment map/checkerboard for eval calibration | Yes — designed explicitly for cross-session relighting; this is the field's standard benchmark |
| **SOL-NeRF** | SIGGRAPH Asia 2023 (10.1145/3610548.3618143) | NeRF | Hybrid: a **single spherical Gaussian (SG) lobe** for sun, a **first-order SH mixture** for sky; sun color analytically linked to solar elevation angle | **Yes, explicit** — single SG direction parameter for the sun | **Yes, explicit** — separate SH term for sky, physically coupled to sun elevation | Albedo/shading decomposition, not full SVBRDF | Multi-view outdoor photos | Yes — outdoor scene decomposition + relighting is the stated goal |
| **The Sky's the Limit** | 2023 (arXiv:2311.16937) | Neural scene rep. with a neural directional-distance function for sky visibility | Neural illumination prior derived from directly-observed sky pixels (rather than masking them out, as prior work did) | Partial — illumination is inferred from sky pixels but not reduced to one discrete sun vector | Yes, explicit — sky pixels are the primary illumination observation | Albedo | Unconstrained outdoor image collections | Yes — reports SOTA on the NeRF-OSR relighting benchmark |
| **Fast Sun-aligned Outdoor Relighting (SR-TensoRF)** | WACV 2024 (arXiv:2311.03965) | TensoRF (fast tensor-decomposed radiance field) | Explicit sun-direction input drives a dedicated shadow-generation branch; no full environment map needed | **Yes, explicit** — sun direction supplied/estimated, aligned per-session from capture deviation | Not separately modeled (subsumed into albedo/shading branch) | Albedo + shadow decomposition | Multi-view outdoor photos across sessions | Yes, targets the NeRF-OSR-style relighting task, optimized for speed |
| **SUNDIAL** | CVPR-W 2024 (arXiv:2312.16215) | NeRF, satellite-imagery domain | Decomposes into **direct (sun) + ambient (sky) + complex** illumination; secondary shadow-ray casting for physically-based disentanglement | **Yes, explicit and jointly optimized** — sun direction solved for jointly with geometry; accurate enough to back out capture time (~5 min) and location (~4 miles) purely from shadows | **Yes, explicit** — "scattered sky illumination" modeled as its own component | Physically-based albedo | Sparse, small-baseline, variable-illumination satellite image sets | Yes — novel view + novel lighting rendering evaluated |
| **GaRe** | ICCV 2025 | Relightable 3D Gaussian Splatting for outdoor scenes | Intrinsic-image-decomposition-based integration of sunlight + sky radiance + indirect lighting, replacing prior "single latent vector per image" compression | Yes (integrated, not a single latent) | Yes (integrated) | Not fully confirmed from abstract | Unconstrained photo collections | Reports diverse shading manipulation + dynamic shadows — implies yes |
| **ROS-GS** | 2025 (arXiv:2509.11275) | Two-stage: 2D Gaussian Splatting for geometry, 3DGS for rendering | Hybrid: **single spherical Gaussian for high-frequency sunlight**, **precomputed radiance transfer (PRT) via SH coefficients for skylight** | Yes, explicit | Yes, explicit | Not detailed in abstract beyond texture decomposition | Multi-view outdoor images + monocular normal priors | Reports SOTA relighting accuracy — implies yes |
| **2DGS Outdoor Decomposition & Relighting (OSDR-GS)** | IJCAI 2025 | 2D Gaussian Splatting | Learns "irrelevant environmental light" per view as a nuisance term to be factored out | Not confirmed | Not confirmed | Not confirmed from search snippet | Multi-view outdoor images | Not confirmed |
| **Relightable 3D Gaussians for Outdoor Scenes in the Wild** | 2026 (SCITEPRESS) | 3DGS | MLP maps per-image embeddings to SH coefficients for sky color/environment light | Not confirmed as separately explicit from sky term | Yes, explicit (SH-parameterized) | Not confirmed | Unconstrained multi-view/multi-time outdoor collections | Implied yes |
| **LightCity** | 2026 (arXiv:2602.01118) | Urban dataset (not a method) | N/A — provides >300 sky maps across a full day for controllable illumination | N/A (dataset) | N/A (dataset) | N/A | Synthetic urban renders w/ GT shadows | Dataset only, but explicitly built for multi-illumination outdoor inverse rendering evaluation |

**Nuance on NeRF-OSR (the field's foundational benchmark).** NeRF-OSR is the clear ancestor of this entire line: its SH-based global illumination + dedicated shadow network established the "decompose outdoor appearance into spatial occupancy + illumination + shadowing + albedo" template that SOL-NeRF, Sky's-the-Limit, SR-TensoRF, ROS-GS, and GaRe all refine. Its own lighting model does **not** separate sun from sky as distinct physical terms — that separation (explicit SG-sun + SH/PRT-sky) is a *post*-NeRF-OSR development, arriving with SOL-NeRF (2023) and maturing through ROS-GS/GaRe (2025). This is directly useful: it shows the sun/sky decomposition IRIS lacks has a several-papers-deep track record of working well for outdoor scenes specifically, with SOL-NeRF's "single SG for sun + low-order SH for sky" being close to minimal-complexity and thus a natural template to adapt.

**What transfers to IRIS specifically:** SOL-NeRF's and ROS-GS's lighting parameterization (SG sun lobe + low-order SH or PRT sky term) is lightweight (a handful of learnable scalars/vectors, not a full envmap network) and slots naturally into IRIS's existing two-term emitter interface (`AreaEmitter`/`SLFEmitter` in `model/emitter.py`) as a *third* term queried specifically when a ray both misses the mesh and originates from inside a window aperture — i.e., it is architecturally a drop-in addition rather than a redesign. None of these methods, however, model *transmission through an aperture into an interior* — they are exterior-facing-camera methods; the "camera indoors, sun/sky visible only through a window" case is untouched by this entire section.

## 4. Sun/shadow geometry estimation (single/multi-view)

| Method | Venue/Year | Task | Input | Output | Relevance |
|---|---|---|---|---|---|
| Lalonde et al., "Estimating Natural Illumination from a Single Outdoor Image" | ICCV 2009 (foundational, pre-deep-learning) | Recover sun position + sky appearance from one image | Single LDR outdoor photo | Sun/sky illumination estimate from shadow + sky-appearance cues | Establishes the classical shadow/sky-cue approach later methods replace with CNNs |
| "Shadow Detection and Sun Direction in Photo Collections" | 2015 (IEEE) | Sun direction from shadow detection across a photo collection | Multi-image collections of a single scene/landmark | Per-image sun direction | Multi-view (not single-image) shadow-based sun estimation precedent |
| "Sun Orientation Estimation from a Single Image using Short-Cuts in DCNN" | 2019 (ScienceDirect) | End-to-end CNN sun-orientation regression | Single outdoor image | Sun azimuth/elevation | Confirms deep single-image sun-direction regression is mature/solved-enough to be a usable prior |
| "Deep Sky Modeling for Single Image Outdoor Lighting Estimation" | CVPR 2019 (arXiv:1905.03897) | Full outdoor illumination (sun+sky) from one image | Single image | Parametric sky model params + sun position | Combines sun-direction with sky-appearance estimation in one network |
| "All-Weather Deep Outdoor Lighting Estimation" | CVPR 2019 (arXiv:1906.04909) | Outdoor HDR lighting estimation robust to weather/time | Single image | HDR sky/sun parametric estimate | Broadens sun/sky estimation beyond clear-sky assumption |
| **SUNDIAL** (also in §3) | CVPR-W 2024 | Joint geometry + sun-direction solve from shadows, multi-view | Sparse satellite multi-view images | Sun direction accurate to ~5 min of local time via shadow ray-casting | Strongest evidence that **multi-view shadow-based sun-direction recovery is a solved, accurate technique** — directly reusable idea for a "Mode B" (geometry-only, no metadata) sun estimator for IRIS scenes with visible sun patches |
| "Multi-View Intrinsic Images of Outdoor Scenes with an Application to Relighting" | (classical multi-view intrinsic imaging) | Combine known/estimated sun direction with multi-view 3D reconstruction + intrinsic decomposition | Multi-view images + approximate geometry + sun direction input | Albedo/shading/relit renders | Precedent for combining an externally-supplied sun direction with multi-view geometry — closer to a "Mode A" (metadata-driven) design |
| OutCast | 2022 (arXiv:2204.09341) | Single-image outdoor relighting w/ cast-shadow synthesis | Single image | Relit image w/ correct new cast shadows | Shows shadow rendering quality is a first-class deliverable, not just a nuisance to remove |

**Takeaway:** sun-direction recovery — both from metadata-free shadow/geometry cues (single-image CNNs, or SUNDIAL's multi-view shadow-ray-casting) and from externally supplied capture metadata — is a mature, largely solved sub-problem in the *outdoor* literature. Nothing surveyed applies this machinery to recovering sun direction from evidence **visible only as a sun patch on an interior floor seen through a window**, which is geometrically a related-but-distinct cue (the window aperture acts as a pinhole/gnomon rather than an object casting a shadow on open ground).

## 5. Window detection & window/environment-map estimation

| Method | Venue/Year | Task | Output | Relevance/limitation |
|---|---|---|---|---|
| "Window Detection in Facade Imagery: A Deep Learning Approach Using Mask R-CNN" | 2021 (arXiv:2107.10006) | 2D window instance segmentation in building-facade photos | 2D bounding boxes/masks | Exterior-facing, 2D only — does not recover 3D aperture geometry or indoor-side context; would need adaptation (or a different exterior-vs-interior detector) to identify windows from the inside |
| "Energy Function Algorithm for Detection of Openings in Indoor Point Clouds" | ISPRS 2019 | Detect wall openings (windows/doors) in indoor point clouds by finding holes in 2D wall projections + energy-function refinement | 3D opening geometry (position, extent) on wall planes | Directly relevant: a concrete, purpose-built method for recovering **3D window aperture geometry from indoor point clouds** — exactly the geometric primitive a window-transmission model would need, though it is a classical (non-learned) geometric pipeline, not integrated with any inverse-rendering/radiance pipeline |
| "Semi-automated Indoor Geometry Reconstruction for Daylight Simulation" | 2025 (ScienceDirect) | Semi-automatic pipeline turning point clouds into watertight, window-containing meshes for daylight simulation | Watertight mesh with explicit window/opening geometry, for use in Radiance-style daylight simulators | Closest found precedent for "explicit window geometry as an input to a physically based renderer" — but the goal is forward daylight *simulation* (architecture/engineering use, Radiance backend) with known glazing properties, not inverse recovery of material/illumination from photographs; not a differentiable/learned pipeline |
| "A Semantic Parsing Method for Indoor Scene Images Based on Prior Knowledge of Building Structure" | JoVE/other | Couples transformer visual features with Manhattan-world 3D priors for semantic indoor reconstruction (walls/windows/doors as structural classes) | Semantic 3D structure incl. openings | Confirms window/door/wall semantic classification from indoor imagery is an active sub-task, generally folded into general indoor scene parsing rather than treated as a distinct research problem |
| **EverLight** | ICCV 2023 (arXiv:2304.13207) | Unified indoor/outdoor HDR lighting (envmap) estimation from a single regular image | 360° HDR panorama + parametric spherical-Gaussian light sources, editable (direction/intensity/count) | The one method found that explicitly targets **both** indoor and outdoor illumination with a single model and produces an *editable*, direction-controllable light-source representation — but it estimates a full-scene HDRI from a single photo (data-driven hallucination of unseen surroundings), it does not model a window as a geometric transmission aperture, and it was not evaluated for physical accuracy of solar geometry (no ground-truth sun-direction metric reported) |
| Gardner et al., "Deep Parametric Indoor Lighting Estimation" | ICCV 2019 | Parametric (few-lobe) indoor lighting estimate from a single LDR image | Discrete parametric light sources (position/intensity/size) | Foundational single-image indoor lighting estimation; light sources modeled are generic (lamps), not distinguished as windows vs. fixtures |
| "Lighthouse" (Srinivasan et al.) | 3DV/ECCV-era | Predict a spatially-coherent lighting volume for indoor scenes from stereo/limited views | Volumetric incident-lighting representation | Cited comparably to Gardner/EverLight; volumetric lighting prediction but not window-specific |
| "HDR Environment Map Estimation with Latent Diffusion Models" | 2025 (arXiv:2507.21261) | Single-image HDR envmap estimation via diffusion prior | Full HDR envmap, good enough to light mirror-reflective insertions | Shows generative-prior envmap estimation is SOTA-competitive in 2025, but again a single global-envmap hallucination, not a geometry-grounded window/sun recovery |
| "360U-Former" | ECCV-W 2024 (arXiv:2410.13566) | Panoramic-ViT-based HDR illumination estimation | HDR panorama | Architecture note (transformer for panoramic illumination), same "estimate one global envmap" paradigm as EverLight/Gardner |

**Takeaway:** window-aperture geometry recovery (from point clouds) and window-appearance segmentation (from facade photos) both exist as **separate, mature, but non-differentiable/non-inverse-rendering** techniques — neither is integrated into a photometric material/lighting optimization loop. Illumination-estimation methods (EverLight, Gardner, Lighthouse, diffusion-envmap methods) solve a related but different problem: hallucinating a plausible global envmap from a photo, rather than grounding a sun/sky estimate in explicit, geometrically located window apertures with physically meaningful transmittance.

## 6. Transparent / refractive / transmissive material recovery

| Method | Venue/Year | Task | Representation | How transmission/IOR modeled | Data | Relevance/limitation |
|---|---|---|---|---|---|---|
| "Differentiable Refraction-Tracing for Mesh Reconstruction of Transparent Objects" | SIGGRAPH Asia 2020 | Recover 3D shape of a transparent *object* via differentiable refraction tracing | Explicit mesh | Ray-traced Snell's-law refraction through recovered surface, single known/assumed IOR | Multi-view images of an isolated transparent object (e.g. glassware) against a known background | Object-level, not scene/window-level; establishes differentiable-refraction as tractable |
| "Transparent Object Reconstruction via Implicit Differentiable Refraction Rendering" | SIGGRAPH Asia 2023 | Same task, implicit (SDF) representation | Neural SDF | Differentiable refraction through the implicit surface | Multi-view images of a single transparent object | Same object-level scope; improves robustness via implicit rep. |
| **TransparentGS** | SIGGRAPH 2025 (arXiv:2504.18768) | Fast inverse rendering of transparent *objects* within otherwise-opaque scenes, using Gaussian Splatting | "Transparent Gaussian primitives" + deferred-refraction rendering strategy; "GaussProbe" light-field probes for ambient/nearby-content lighting | Refraction handled per-Gaussian via deferred refraction (not a classical mesh-based Snell's-law trace); IOR/material parameterization not confirmed from abstract | Multi-view images of a scene containing a transparent object | Closest transparent-material method to "fast, scene-embedded transmissive rendering," but explicitly targets discrete objects (e.g. a glass on a table), and abstract does not confirm applicability to a large planar aperture like a window pane set into a wall |
| "DiffTrans: Differentiable Geometry-Materials Decomposition for Reconstructing Transparent Objects" | 2026 (arXiv:2603.00413) | Joint geometry+material recovery for transparent objects | Differentiable rendering, explicit geometry+material split | Not confirmed from search snippet | Multi-view images | Object-level, very recent (2026) — same scope limitation as above |
| "Reconstructing Translucent Objects using Differentiable Rendering" | SIGGRAPH 2022 (Deng et al., Cornell) | Recover shape+material of *translucent* (subsurface-scattering) objects | Differentiable path tracing | Subsurface scattering model, not thin-dielectric transmission | Multi-view images | Different physical regime (SSS, not clear-glass transmission) but shares the differentiable-rendering-for-non-opaque-materials goal |
| **NEMTO** | 2023 (arXiv:2303.11963) | Neural environment matting for novel-view/relighting synthesis of transparent objects | Neural implicit + environment matting | Learned refraction/matting rather than explicit Snell's law | Multi-view images of a transparent object under known/varying background | Object-level; environment-matting approach is an alternative to explicit-IOR ray tracing worth noting as a simpler proxy |
| Mitsuba/PBR-book thin-dielectric BSDF (`dielectric.cpp`, PBR book §9.5) | Standard PBR reference (not a paper contribution, but a directly usable primitive) | Analytic thin-slab dielectric BSDF: reflected lobe + undeflected transmitted lobe via a closed-form sum over the internal-reflection geometric series | N/A — it's a BSDF formula | Exact for a thin, planar, uniform-IOR slab (i.e. a good physical model for a *pane of window glass*, as opposed to thick refractive objects) | N/A | **Directly relevant as a ready-made, differentiable-renderer-native (Mitsuba has it built in) material model for a window pane** — since IRIS already runs on Mitsuba 3, the thin-dielectric BSDF plugin is a much smaller lift than building a full refraction-tracing pipeline like TransparentGS, provided a window is represented as its own (thin, planar) shape rather than folded into the room mesh |

**Takeaway:** the transparent/refractive inverse-rendering literature is uniformly **object-centric** (a glass, a vase, a transparent figurine reconstructed against a background), optimizing full 3D shape *and* material jointly for an isolated object with unknown geometry. None of the surveyed work addresses the window case, which is actually a much narrower and more constrained sub-problem: the aperture's *planar* geometry is largely known/recoverable from room structure (per §5's point-cloud opening-detection work), so what's missing is not object-shape recovery but a transmittance *material* term — for which the standard thin-dielectric BSDF (already implemented in Mitsuba, IRIS's renderer) is architecturally a much closer fit than any of the learned object-reconstruction methods surveyed.

## 7. Dataset papers noted in passing

(A full dataset audit against required properties — windows, sun patches, multiview, poses, timestamps, HDR/RAW, license — is being done separately per `PROJECT_STATUS.md`; these are only the dataset papers encountered during this literature pass.)

- **NeRF-OSR benchmark** (arXiv:2112.05140): 8 outdoor building sites, 3240 views, 110 sessions/times — the standard outdoor relighting benchmark; no indoor/window component.
- **OpenRooms** (arXiv:2007.12868) / **InteriorVerse**: synthetic indoor HDR scenes with GT material, some window-lit scenes, but daylight is not a distinguished/labeled phenomenon.
- **LightCity** (arXiv:2602.01118): urban outdoor dataset, >300 sky maps across a full day — relevant as a template for "many illumination conditions of the same static geometry" dataset design, but urban/outdoor not indoor.
- **A Real-world Display Inverse Rendering Dataset** (arXiv:2508.14411): real-world inverse rendering data, not daylight-focused per the snippet found.
- ScanNet++ (used by IRIS itself for 2 of its 8 released scenes): real-world indoor scans; per the architecture audit, IRIS hardcodes exposure=1.0 for every ScanNet++ frame and loads no solar/temporal metadata for it.

## Summary of section-by-section transfer opportunities

1. **From FIPT/IRIS itself:** the existing SLF (voxel radiance cache) is architecturally the natural attachment point for a new "sky visibility through aperture" cached field — it's already a per-voxel queryable radiance structure in the renderer.
2. **From outdoor daylight-aware NeRF/GS (§3):** SOL-NeRF's and ROS-GS's "single SG sun lobe + low-order SH or PRT sky term" is a lightweight, empirically validated sun+sky parameterization that could be added as a third emitter term in `model/emitter.py`, evaluated only for rays that both miss the mesh and pass through a window aperture.
3. **From sun-geometry estimation (§4):** SUNDIAL's shadow-ray-casting joint sun-direction solve demonstrates that a metadata-free ("Mode B") sun-direction estimate from visible sun-patch/shadow evidence is achievable to high accuracy in an unrelated domain (satellite imagery) — the analogous cue for IRIS would be the sun patch's position/shape relative to the window aperture acting as a pinhole.
4. **From window geometry recovery (§5):** the ISPRS point-cloud opening-detection energy-function method and the daylight-simulation semi-automated reconstruction pipeline are direct precedents for recovering explicit window aperture geometry from the same class of input (indoor point cloud/mesh) IRIS already consumes — this is a preprocessing step that could run before/alongside IRIS's existing mesh loading, rather than requiring new capture.
5. **From transmissive materials (§6):** Mitsuba's built-in thin-dielectric BSDF is a much smaller implementation lift than the object-centric transparent-reconstruction literature (TransparentGS, DiffTrans, NEMTO) — appropriate because the window's *geometry* is a much better-constrained sub-problem here than in those papers (planar, roughly axis-known from wall structure) even though its *material* (transmittance/IOR) still needs recovery.
